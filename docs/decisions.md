# Default decisions (provisional)

These values are **design defaults**, not final choices. They may be revised
in phase B (once Azure OpenAI is available) or when workshop feedback calls for
it. The judge thresholds and rubrics are calibrated at that point too: see
[team-validation.md](team-validation.md).

## Compaction threshold

- **Provisional values:** 8 turns (`COMPACTION_MESSAGE_THRESHOLD`,
  `settings.compaction_message_threshold`), 2 turns kept as they are
  (`COMPACTION_KEEP_TURNS`, `settings.compaction_keep_turns`).
- **Meaning:** once the context holds this number of turns at the start of a
  turn, the *harness* clears every older tool result (marker in place of the
  result) and replaces the turns before the last `COMPACTION_KEEP_TURNS` by a
  rolling summary under five fixed headings, written by a separate model call
  with `my-agent/compaction_prompt.md`.
- **Status:** starting point for the simulated tests of workshop 07. The
  fidelity of the summaries produced by the real model, and the threshold
  itself, will be calibrated in phase B.

## Corpus metadata schema

- **Provisional choice:** a single `corpus/metadata.yaml` file next to the
  `.txt` files, rather than a front matter in each file or a `.meta` file per
  document.
- **Current fields:** `id`, `file`, `title`, `version`, `organization`,
  `audience`, `address`, and the optional boolean `retired`.
- **Alternatives set aside for now:**
  - a YAML front matter at the top of each `.txt` (closer to the source file,
    but it mixes teaching text and metadata);
  - a `name.txt.meta` file next to each source (more local, but more files to
    maintain).
- **Status:** revisable as long as the index stays rebuildable from the
  versioned corpus. Changing the schema will require adapting
  `business/docs_search/src/docs_search/indexing.py` and `business/docs_search/tests/test_docs_search.py`.

## Azure deployment names

No deployment name is hard-coded. They are **fully configurable** through
environment variables (see `.env.example`):

| Role | Variable |
|---|---|
| Agent (chat) | `AZURE_OPENAI_CHAT_DEPLOYMENT` |
| Judge | `AZURE_OPENAI_JUDGE_DEPLOYMENT` |
| Embeddings | `AZURE_OPENAI_EMBEDDINGS_DEPLOYMENT` |
| Fallback (workshop 18) | `AZURE_OPENAI_FALLBACK_DEPLOYMENT` |
| Reranking (optional) | `AZURE_OPENAI_RERANKING_DEPLOYMENT` |

The values stay empty during design: the proxy runs in simulated mode. The
actual Azure deployment names will be set in phase B (decision D4 of the plan).
The `AZURE_OPENAI_API_KEY` key stays on the server, never committed.

## Language

Rule: **code and technical docs in English; workshop guides and the agent in French.**

- English: code, identifiers, comments, technical documentation (`docs/`), test
  names, assertion messages, log and error messages of the kit, YAML keys,
  trace fields, API routes and field names, business codes (`delivered`,
  `pending`, `customer_service`...).
- French: the workshop guides (`workshops/*/README.md`, `workshops/*/contrat.md`, `workshops/17-evaluation/routes/README.md`),
  written for the French-speaking reader of the book and using its terms as they are
  ("borner et déclarer", "mention", "harnais", "boucle d'agent"...). The names they quote
  (trace fields, events, tools, parameters) stay English, as in the code.
- French: everything the agent's user reads or types. In the tests, that is
  the user turns sent to the agent, the expected phrases and keywords in its
  answers, the simulated proxy replies, the attachment fixture of workshop 15
  and the corpus `.txt` texts the agent quotes (with their `title` in
  `corpus/metadata.yaml`; the keys stay English).
- Business data shown to the user: the codes stay English in the API, and
  the display labels are French (`coded_values` of the business API sources,
  `ROLE_LABELS` in `business/business_api/src/business_api/auth.py`), so that answers
  read naturally in French.
- Proper nouns (people, companies, cities) and the book title stay French.
- LLM-judge rubrics are written in English, but each `criterion` states that
  the agent answers in French; `JUDGE_INSTRUCTIONS` (sent to the real judge in
  phase B) says to judge the French answer and to fail an answer that is not in
  French. During design, `looks_french()` applies that rule structurally.
- Chat interface strings: the standard Chainlit UI consumes the conversation
  SSE API. Its welcome message and UI resources live in `clients/chat_ui/`
  and are in French. The strings produced by the agent (answers, mentions, confirmation requests) are
  the student's and must be French. The few strings generated by the kit
  itself (for example "Your turn: implement the system prompt...") are
  addressed to the student as a developer, not to the end user, so they stay
  English in the API; the browser client presents a French explanation.
- Student-side choice: the system prompt and tool descriptions the student
  writes may be in either language; only the answers must be French.

The book itself is written in French; the workshop guides, in the same language, refer to it by
chapter number and reuse its terms. The expected French patterns are calibrated again in phase B.

## Judge: facts first, then meaning, repeated

- **Order:** what code can check (application state, traces, logs, interface events) is
  asserted first; a rubric then judges the meaning (`tooling/evaluation/src/evaluation/judge.py`):
  a structural layer (required or forbidden patterns) always, then a semantic layer by a
  judge model when `JUDGE_MODE` is `auto` and `JUDGE_BASE_URL` is set, or always when
  `JUDGE_MODE=semantic`. A failed semantic verdict fails the test.
- **Repetition:** a rubric applied to a fresh conversation is replayed with
  `apply_rubric_repeatedly` and passes when `JUDGE_K` runs out of at most `JUDGE_N` pass
  (3 out of 5 by default); it stops as soon as the outcome is known. Rubrics on an answer
  that cannot be replayed (a continuation of a conversation) are applied once. Each run starts
  with a fresh proxy quota (`DAILY_TOKEN_QUOTA`), as each test does; the evaluation routes of
  workshop 17 run once each (`ROUTE_K` out of `ROUTE_N`, 1 out of 1 by default).
- **Inert agent:** `workshop check-inert` runs every workshop test against an agent that
  answers a cautious French sentence without calling the model nor any tool, and fakes the
  file deliverables; every test must fail. It guards against tests passed by doing nothing.
  This agent is the bootstrap of `my-agent/` overlaid by `tooling/cli/inert_agent/` (an
  inert `harness.py` and the facade deliverables), assembled in a temporary folder; the command
  refuses to run once `my-agent/` differs from the bootstrap recorded in
  `tooling/cli/inert_agent/bootstrap.sha256`.
- **Connected bootstrap:** the bootstrap `my-agent/harness.py` already converses through the
  model (system prompt, history, answer, trace written with `agent_sdk.trace.Tracer`), so
  students start from a working agent. `workshop check-bootstrap` therefore tolerates the tests
  listed in `tooling/cli/bootstrap_passes.txt` and fails on any other passing test;
  `check-inert` tolerates none.

## Superseded tests

A workshop sometimes deliberately reverses an earlier one (workshop 03 has no tool, workshop
04 adds one). Such a test is marked `@pytest.mark.superseded_by("04")`
(`tooling/testkit/src/testkit/superseded.py`): `workshop check <id>` sets `WORKSHOP_TARGET=<id>`,
and the test is skipped, with an explicit reason, once the target reaches the marker.

## Private generalization tests

Next to a public test file, `test_workshop_<id>_private.py` checks the same success criteria
with other inputs (other customers, references, wordings, users, thresholds, attachments in
`tests/fixtures_private/`): an implementation tuned to the public cases fails them. They are
for the trainers, not the students:

- they are deselected unless pytest gets `--private` (`tooling/testkit/src/testkit/private.py`);
  `workshop check <id> --private` runs them, `check-inert` and `check-bootstrap` always include them;
- `.gitattributes` marks them `export-ignore`: the student material is produced with
  `git archive`, which leaves them out.

Workshops 09, 14, 17 and 19 have tests with no input to vary (catalog, manifest, routes): those
tests have no private variant, and workshop 19 has no private file.

## Simulated and live modes

The live mode is the reference for every workshop, workshop 03 included: the guides and the
rubrics are written for a real model. From workshop 04 on it is also required, because the
simulated model does not call tools on its own and a test passed in simulated mode would reward
a hard-coded workflow. The simulated mode only serves the CI, `check-bootstrap` and `check-inert`;
it remains usable to start workshop 03 without Azure access.
